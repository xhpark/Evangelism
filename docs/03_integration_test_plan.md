```
[앱 실행] ➔ [저작권·개인정보 별도 필수 동의] ➔ [일회용 코드 활성화] ➔ [메인 5대 탭]
```

## 3. 실기기 빌드 및 배포 명령어

```bash
# 디버그 APK 빌드
flutter build apk --debug --dart-define=LICENSE_API_URL=<배포 URL>

# 실기기(Galaxy S24 Ultra) 설치 및 실행
adb -s R3CX60PDSTA install -r build/app/outputs/flutter-apk/app-debug.apk
adb -s R3CX60PDSTA shell am start -n com.evangelism.just_ee.just_ee_master/.MainActivity
```

## 4. 검증 상태 표기 기준 (2026-08-29 추가)

* **PASS**: Galaxy S24 Ultra 실기기에서 실제로 수행하여 통과를 확인한 항목.
* **미검증**: 코드에는 반영되었으나 아직 실기기 확인을 하지 않은 항목. 실기기 검증 후 담당자가 PASS로 갱신해야 합니다.
  - 2026-09-02 변경분 중 `IT-01`은 실기기 PASS, `IT-15`와 `IT-17`은 일부 실서버 경계를 통과했습니다. `IT-14`, `IT-16`, `IT-18`과 각 부분 PASS의 남은 단계는 계속 미검증입니다.

### 검증 이력

* **IT-17 구 프로토콜 (2026-08-29 야간)**: 당시 앱 → 요청 서명 → Apps Script 백엔드 → 관리 시트 기록까지 전 구간을 Galaxy S24 Ultra에서 확인했습니다.
  이 항목은 앱의 HTTP 타임아웃이 Apps Script 콜드 스타트(실측 5,024ms)보다 짧아 계속 실패하던 것을 20초로 늘린 뒤 통과했습니다(커밋 `fd7ba57`).
  이 결과는 2026-09-02 제거된 공유 서명/PIN 프로토콜의 이력이며, 현재 일회용 코드·기기 토큰 프로토콜의 PASS 근거로 재사용하지 않습니다.

* **2026-09-02 재검증 시도**: 저장소 이력에서 운영 엔드포인트를 복구해 URL을 노출하지 않고 GET/POST 상태를 확인했습니다. 서버는 접근 가능하지만 아직 **구형 프로토콜**을 실행합니다. 연결된 Apps Script CLI/Drive 계정에서는 해당 프로젝트가 식별되지 않아 안전한 배포를 중단했습니다.
* 같은 시점에 `adb devices -l`, ADB mDNS, 이전 무선 연결 기록, USB ADB 인터페이스를 확인했지만 연결 가능한 Android 단말이 없었습니다. 따라서 IT-15~IT-18의 실서버·실기기 상태는 계속 **미검증**입니다.
* **2026-09-02 USB 재연결**: `R3CX60PDSTA / SM-S928N / Android 16`을 `device` 상태로 확인했습니다. 설치본 `1.0.0+1`은 예상 패키지·라벨이며 로컬 release 키와 서명이 일치하고, 정확한 패키지를 실행해 콜드 스타트 동의 게이트까지 확인했습니다. 설치본의 동의 체크는 미완료이고 마이크 권한은 거부 상태이므로 사용자 승인 전 탭·TTS·STT 결과를 PASS로 바꾸지 않습니다.
* 새 코드는 업데이트 식별을 위해 `1.0.1+2`로 올렸습니다. 운영 서버가 새 토큰 프로토콜로 배포되지 않아 처음에는 설치를 보류했으며, 아래와 같이 사용자의 명시적 테스트 설치 요청 후에만 placeholder 빌드를 설치했습니다.
* 새 백엔드 배포 직후에는 GET health 응답의 `protocol=device_token_v2`를 확인한 뒤 실제 URL APK를 빌드합니다.
* **검증용 설치 실행**: 사용자 요청에 따라 placeholder 서버 주소로 fresh release APK를 빌드하고 `adb install -r`로 `1.0.1+2`를 설치했습니다. 설치 전후 앱 데이터 inode가 같고 first-install 시각도 유지됐으며, 단말에서 읽어 온 APK의 SHA-256은 빌드 산출물과 일치했습니다.
* 정확한 패키지 실행 후 `Version 1.0.1+2`, 저작권·개인정보 2개 동의 체크박스, 미동의 상태를 확인했습니다. 사용자가 두 동의를 완료하기 전이므로 IT-01의 전체 흐름과 활성화 이후 항목은 아직 미검증입니다.
* **실서버 빌드 준비**: 사용자가 제공한 배포 URL은 URL 형식, HTTP 200, `status=OK`, `protocol=device_token_v2`를 통과했습니다. URL을 저장소에 기록하지 않고 실제 URL release APK를 fresh build해 package/version/label/V2 서명을 확인했습니다. 당시 설치 직전 단말이 ADB에서 분리되어 첫 산출물은 설치하지 않았습니다.
* **실서버 APK 설치**: 단말 재연결 후 서버 health를 다시 확인하고 실제 URL release APK를 재빌드했습니다. 서명·패키지·버전을 검증한 뒤 `adb install -r`가 성공했으며, 단말에서 다시 추출한 APK의 SHA-256이 빌드 산출물과 일치했습니다. 설치 전후 앱 데이터 inode와 최초 설치 시각도 유지됐습니다.
* **활성화 호환성 수정 및 실서버 검증**: 기존 1.0.0의 3그룹 기기 코드가 새 서버의 4그룹 검증에서 거부되는 원인을 확인했습니다. 앱이 사용자 데이터를 유지한 채 기기 코드를 4그룹으로 1회 확장하도록 수정한 release APK를 동일 서명으로 업데이트했습니다. 사용자가 두 동의를 완료하고 기존 `UNUSED` 코드로 활성화에 성공했으며, 시트의 `USED` 전환·사용 기기/시각·`APPROVED` 라이선스·토큰 해시를 확인했습니다. 같은 코드를 별도 진단 기기로 다시 요청했을 때 실서버가 `DENIED`를 반환하고 라이선스 행이 늘지 않았습니다. 백그라운드 복귀 후 최근 접속 시각도 갱신됐습니다.
* 실서버 APK 최초 실행 당시 정확한 패키지는 정상 실행됐고 치명적 Flutter/AndroidRuntime 예외가 없었습니다. 그 시점에는 동의가 `0/2`였으며, 이후 사용자가 직접 동의하고 위 활성화 호환성 검증을 완료했습니다.
